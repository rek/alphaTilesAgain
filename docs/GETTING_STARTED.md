# Getting Started

Everything needed to set up and work in this repo.

## Initial Setup

```sh
nvm use 22
npm install
```

## Development

### Running the App

```sh
APP_LANG=eng nx start alphaTiles      # Metro bundler
nx start-web-eng alphaTiles           # Web dev server — eng (http://localhost:8081)
nx start-web-yue alphaTiles           # Web dev server — yue (http://localhost:8081)
APP_LANG=eng nx run-android alphaTiles
APP_LANG=eng nx run-ios alphaTiles
```

> `start-web-*` regenerates the lang manifest before starting — no separate regen step needed.

> Tip: `nx show project alphaTiles` lists all available targets.

### Switching Language During Dev

`APP_LANG` selects the language pack. To switch:

1. Regenerate the manifest for the new language:
   ```sh
   APP_LANG=yue node_modules/.bin/tsx tools/generate-lang-manifest.ts
   ```
2. Restart the dev server with the new `APP_LANG`:
   ```sh
   APP_LANG=yue nx serve alphaTiles
   ```

Metro does not watch `APP_LANG` — a full restart is required. The manifest regeneration step is also required because `langManifest.ts` is generated once and the dev server reads it as a static import.

### Validating a language pack

Run after any change to files under `languages/<code>/`:

```sh
APP_LANG=yue node_modules/.bin/tsx tools/validate-lang-pack.ts
```

The validator checks audio/image references, tile structure, word cross-refs, and more.
It must pass before `generate-lang-manifest.ts` is run — CI enforces this order.
Use `nx validate-lang-pack alphaTiles` only when `PUBLIC_LANG_ASSETS` is set (it also triggers rsync from the source repo).

## Language Pack Setup

Language pack text files, fonts, images, and audio are committed to the repo under `languages/`. After cloning, only `APP_LANG` is needed to run the app:

```sh
export APP_LANG=eng   # selects the language pack (eng, tpx, template, yue)
```

Set this in your shell profile (`~/.zshrc` or `~/.bashrc`). Without it, `nx start` will fail with an actionable error.

### Updating a language pack

To pull in new content from the `PublicLanguageAssets` source repo, you also need `PUBLIC_LANG_ASSETS`:

```sh
export PUBLIC_LANG_ASSETS=/path/to/PublicLanguageAssets
./nx rsync-lang-pack alphaTiles
./nx validate-lang-pack alphaTiles
./nx generate-lang-manifest alphaTiles
# commit changes to languages/ and langManifest.ts
```

## Web Export (GitHub Pages)

The app is exported as a static site and deployed to GitHub Pages via CI.
Each language gets its own sub-path: `/alphaTilesAgain/<langSlug>/`.

### Building locally

```sh
APP_LANG=eng EXPO_BASE_URL=/alphaTilesAgain/engEnglish4 npx nx run alphaTiles:web-export
```

`EXPO_BASE_URL` **must include the repo name** (`/alphaTilesAgain/...`). Without it,
`experiments.baseUrl` stays empty and all HTML asset paths are root-absolute, causing
404s on GitHub Pages. See **ADR-011** for the full explanation.

### Adding a new language to CI

In `deploy.yaml`, add a build step and a stage step following the eng/yue pattern.
Set `EXPO_BASE_URL: /alphaTilesAgain/<langSlug>` to match the stage directory name.

## Local Builds

### Requirements

- **Java 21** (openjdk 21.0.8)
- **Android Studio** with:
  - SDK Platforms: Android 15
  - SDK Tools: CMake, Android SDK Build-Tools, Android SDK Platform-Tools

### Build APK

```sh
APP_LANG=yue nx buildApk alphaTiles   # → dist/apps/alphaTiles/alphaTiles-yue.apk
```

Runs `eas build --local` with the `<APP_LANG>-apk` profile in `apps/alphaTiles/eas.json`: clean prebuild, lang manifest regenerated by the `eas-build-post-install` hook, signed with the EAS-managed release keystore (needs `eas-cli` + `eas login`; never the debug key). Store builds: `eas build --profile yue` from `apps/alphaTiles`.

## EAS Updates (OTA)

AlphaTiles uses **EAS Update** to ship JS bundle + asset changes to installed apps without a store review cycle. Each language build has its own channel, `<lang>-production` (`yue-production`, `eng-production`), set per build profile in `apps/alphaTiles/eas.json`. A binary only receives updates from its own channel, so the channel in `eas.json` and the one you publish to must match. See `docs/decisions/ADR-009-ota-via-eas-update.md` and `openspec/changes/ota-updates/design.md`.

### Owner-only one-time checklist (do NOT automate)

- [ ] `eas login` with the `alpha-tiles` Expo org account.
- [ ] Confirm the EAS project exists (`eas project:info` in `apps/alphaTiles`). `app.config.ts` reads `EAS_PROJECT_ID` from env, falling back to the committed ID; run `eas init` only if no project exists, and never twice (duplicate projects).
- [ ] Set `EAS_PROJECT_ID` as an EAS/CI secret if you override the committed ID.
- [ ] Android credentials (release keystore) via `eas credentials` / first `eas build`; iOS Apple credentials likewise when iOS ships.
- [ ] First store build per language with the matching profile (`eas build --profile yue`). OTA only reaches binaries built after this.

### Publishing a content update

```sh
npm run update:yue                                  # or: APP_LANG=yue nx publish-update alphaTiles
UPDATE_MESSAGE="fix tile audio" npm run update:yue  # custom message
npm run update:eng                                  # same scheme for other languages
```

This validates the lang pack and regenerates the manifest (`prebuild-lang`) with that `APP_LANG`, then runs `eas update --channel yue-production` from `apps/alphaTiles`. Installed apps check on launch, download in the background, and apply on the next cold start (two launches after publish).

### OTA vs. store release

| Change type | Ship via |
|-------------|----------|
| JS logic / UI | OTA |
| Bundled images / audio, language-pack content fixes | OTA |
| New native module, Expo SDK bump, new `app.config.ts` plugin | Store release |
| `android.package` / `ios.bundleIdentifier`, permissions, icon/splash native config | Store release |
| Any change that needs a new `APP_VERSION` | Store release |

`runtimeVersion` uses the `appVersion` policy: an update only reaches binaries whose version equals `APP_VERSION` at publish time. Content-only changes do not touch it.

### Bumping APP_VERSION

For a native/store release, edit `APP_VERSION` in `apps/alphaTiles/app.config.ts` (e.g. `1.0.0` to `1.1.0`), then `eas build --profile yue` and submit. Android `versionCode` auto-increments remotely. After the bump, OTA updates published from that code only reach the new binary; users on the old binary stay on the old version's updates until they upgrade. Never bump it for an OTA-only change, or no installed app will receive it.

### Rollback

From `apps/alphaTiles`, either republish a known-good earlier update to the channel or roll back to the embedded bundle:

```sh
eas update:list --branch yue-production              # find the good update group ID
eas update:republish --destination-channel yue-production --group <group-id>
eas update:rollback                                  # revert to the binary's embedded bundle
```

Users get the rolled-back version on their next cold start. Rolling back a bad `APP_VERSION` store release means shipping a new store build.

## Store submission (GitHub Action)

`.github/workflows/eas-build.yml` → Run workflow → profile `yue`, tick **submit**. EAS builds the AAB and, when it finishes, submits it to Google Play's **internal** track as a **draft** (`submit.yue` in `apps/alphaTiles/eas.json`). Promote to production in Play Console.

One-time owner setup:
- [ ] Android keystore for `com.makektm.alphatiles` exists in EAS (new package ID — first build must create it: run `eas credentials` or one interactive `eas build -p android --profile yue` locally; `--non-interactive` CI builds can't generate a keystore).
- [ ] Play Console app created for `com.makektm.alphatiles`, and the **first** AAB uploaded by hand (Google requires a manual first upload before API submissions work).
- [ ] Google Play service account JSON key with release permissions, uploaded to EAS (`eas credentials` → Android → Google Service Account).
- [ ] Store listing, content rating, data safety form, target audience (children → Families policy), privacy policy URL (#54).
